# Validation strategy

## 1. Objective

Validation must demonstrate that SeqQC produces correct, reproducible,
understandable, secure, and portable results for its declared scope. It must
separate software verification, scientific method validation, usability, and an
organization's own deployment validation.

## 2. Evidence layers

| Layer | Question |
| --- | --- |
| Unit/property tests | Does each parser, rule, state transition, and calculation behave as specified? |
| Adapter contract tests | Does each external tool/scheduler map to the normalized contract correctly? |
| Golden workflow tests | Does a complete fixed workflow produce the approved result package? |
| Scientific comparison | Do metrics agree with trusted methods and known truth within tolerance? |
| Robustness/security | Does hostile, corrupt, interrupted, or resource-starved behavior fail safely? |
| Cross-platform equivalence | Are normalized results consistent across supported builds/providers? |
| Performance/scale | Does execution remain safe and responsive at declared tiers? |
| Usability/accessibility | Can intended users complete and correctly interpret key tasks? |
| Deployment qualification | Can an institution document its exact environment and intended use? |

## 3. Test-data strategy

### 3.1 Tiny synthetic fixtures

Generate deterministic, non-human fixtures for:

- valid and malformed FASTQ encodings/records/compression;
- single/paired/multilane naming and orphan cases;
- BAM/CRAM flags, CIGARs, tags, duplicates, clipping, sort/index conditions;
- known coverage across tiny references and target intervals;
- RNA exon/intron/intergenic/junction/strand cases;
- unusual contig names, zero-length intervals, overlaps, and boundary cases; and
- malicious filenames, sample sheets, annotations, archives, and tool output.

Expected values are hand-derived or generated by an independently reviewed
reference implementation. Fixtures contain no protected data.

### 3.2 Public benchmark datasets

Use appropriately licensed/public WGS, WES, and bulk RNA-seq datasets during
development validation. Record source, consent/use constraints, checksums, and
permitted redistribution. Large datasets need not live in Git; an offline
validation-site manifest can reference institutionally staged copies.

### 3.3 Perturbation series

Construct controlled series for:

- adapter/quality degradation and base-composition bias;
- read-depth downsampling;
- duplication/library complexity;
- contamination mixtures when permitted;
- coverage dropout and target imbalance;
- RNA degradation/3′ bias, rRNA/mitochondrial content, strandedness;
- batch shifts and sample swaps; and
- file truncation/corruption.

The system must respond monotonically where the metric definition predicts it
and avoid claims where evidence is ambiguous.

## 4. Metric validation record

Every supported metric has a record containing:

- metric and method/tool versions;
- intended input/assay/context and exclusions;
- gold/reference method;
- datasets and ground truth;
- comparison statistics and tolerance rationale;
- supported OS/architecture/executor matrix;
- computational limits;
- known biases/failure modes;
- threshold/preset validation evidence; and
- approver/date/status (`validated`, `conditional`, `investigational`,
  `unsupported`).

## 5. Numerical and categorical acceptance

- Exact counts should match exactly unless parallel/tool semantics justify a
  documented exception.
- Floating metrics use metric-specific absolute/relative tolerances established
  before comparison.
- Distributions compare bin definitions plus total mass and selected quantiles.
- Findings must match the deterministic ruleset exactly.
- Boundary tests cover equality, just inside/outside, missing, NaN/infinite,
  zero denominator, and incompatible units.
- A changed tool/parser/rule version triggers targeted revalidation and a
  comparability assessment.

## 6. Assay validation matrix

### FASTQ

- single/paired, multiple lanes, compressed/uncompressed
- supported short-read quality encodings and read lengths
- clean and perturbed quality/composition/adapter/duplication cases
- truncation and pair disagreement

### WGS

- at least two supported references/species contexts
- coverage depths spanning insufficient to high coverage
- duplicate, GC, insert-size, mapping, contamination/resource availability
- BAM and CRAM with correct/incorrect/missing reference

### WES

- multiple capture-target structures
- padded/unpadded territory, overlap/duplicate interval handling
- on/off-target and uniformity perturbations
- low-coverage gene/target aggregation

### Bulk RNA-seq

- stranded/unstranded and single/paired libraries
- at least two compatible annotations/species contexts
- exonic/intronic/intergenic, junction, rRNA/mitochondrial and degradation cases
- cohort correlation/PCA with known replicate/batch structure

Clinical and preclinical labels do not reduce scientific testing; they add
privacy, policy, and audit scenarios.

## 7. Cross-platform and provider validation

Test supported combinations of:

- Windows, macOS, Linux;
- x86-64 and any declared ARM64 targets;
- beginner bundle and institution-managed tools;
- local, generic import, Slurm, PBS Pro, LSF, and SGE;
- local and mounted network input paths; and
- common path/locale/time-zone conditions.

For each combination record unsupported modules explicitly. UI support must not
be confused with tool/executor support.

QC modules are validated across the declared Windows/macOS/Linux matrix.
Alignment modules are validated only on declared Linux distributions,
architectures, and execution providers for the initial release. Negative tests
verify that Windows/macOS cannot plan or launch an aligner task.

## 8. Workflow reliability tests

- crash/restart at every persisted state transition
- cancellation before/during/after child tasks
- insufficient disk/RAM, permission loss, quota, full scratch
- tool crash, malformed output, unexpected version, executable replacement
- input/reference changes during and after analysis
- stale locks and unreliable network locks
- delayed scheduler accounting, lost jobs, preemption, array partial failure
- migration/backup/restore across supported schema versions
- concurrent read-only access and blocked concurrent write

## 9. Security validation

- Static/dependency/secret scans and SBOM verification
- Fuzz FASTQ/BAM/CRAM metadata parsers, sample sheets, interval/annotation
  parsing, archives, report content, and external tool output
- Command/path injection corpus on every platform
- Archive traversal, symlink, decompression, malformed crypto, and tamper tests
- Key loss/wrong password/key rotation/session timeout tests
- Audit-chain mutation/detection and export tests
- Verify redaction of logs, crash data, process arguments, and temporary paths
- Network-attempt monitoring with a functioning network
- Local API disabled, loopback-only, authentication, origin, rate and audit tests

## 10. Report validation

- Reconcile dashboard, HTML, PDF, JSON, CSV, and TSV values to one report model.
- Validate pagination, long identifiers, Unicode, missing values, large tables,
  plots, themes, and print behavior.
- Open HTML/PDF on offline clean systems with no installed development assets.
- Verify report/source digests and de-identification transformations.
- PDF visual regression uses rendered-page comparisons plus semantic text/table
  extraction.
- Accessible names/summaries and keyboard navigation are tested for dashboard
  and HTML.

## 11. Performance tiers

Benchmarks use fixed hardware profiles and publish input size, sample count,
storage type, concurrency, wall time, peak RAM, scratch, and output size.

| Tier | Planning workload |
| --- | --- |
| Personal | 1–8 samples; laptop resources |
| Workstation | 1–100 samples; multicore/high-memory host |
| Core/HPC | 100–10,000 samples represented; scheduled execution and paged UI |

These are planning test tiers, not guarantees that all assays complete within a
fixed duration. Acceptance thresholds are set after an early benchmark spike.

## 12. Usability and interpretation validation

Representative users complete input discovery, ambiguity resolution, reference
selection, preflight, finding interpretation, provenance lookup, report export,
and recovery. Measure completion, serious errors, time, comprehension, and
confidence. A participant must distinguish:

- operational failure from scientific finding;
- fixed threshold from cohort outlier;
- not evaluated from within range; and
- research-use output from a diagnostic result.

## 13. Organizational validation package

SeqQC should export an offline deployment-evidence bundle containing application
and tool versions/checksums, SBOM, platform, policy/presets, reference manifests,
test protocol/results, known limitations, installation qualification checklist,
and change-impact summary. The institution owns approval for its intended use.

## 14. Release decision

No assay/module changes from “investigational” to “supported” without its metric
records, platform matrix, end-to-end golden tests, documented limitations, and
review. No release proceeds with unresolved evidence corruption, privacy leak,
offline-boundary breach, or irrecoverable project-migration defect.
